# Advanced discovery architecture

Phase 4 extends the existing `/api/v1/jobs` service, canonical PostgreSQL records, Phase 2 freshness and Phase 3 private assessments. It adds no external search service, embedding provider or paid dependency.

## Request flow and limits

React stores applied public criteria in the URL, validates supported fields and submits them to the authenticated jobs API. `SearchParams` performs authoritative validation; `modules/search/query.py` builds parameterized SQLAlchemy expressions, lateral analysis/own-match lookups, database predicates and deterministic ordering. PostgreSQL returns a count and only the requested page. `service.py` presents canonical `JobOut` values and batches saved flags for page IDs. Candidate assessment summaries are a separate private sidecar keyed by the page's job IDs, never fields added to universally shared canonical job data. Detail and comparison evidence use the existing ownership-scoped matching service.

Page sizes are 1–100 (UI 12), pages 1–10,000. Keyword queries are at most 200 characters and 12 terms. Skill filters contain at most 10 names of at most 100 characters. Enum arrays are bounded to the supported choices. Suggestions return at most 12 records; comparisons accept at most 3 distinct UUIDs. Unknown criteria keys, invalid ranges, invalid dates and incompatible salary requests return 422. No authentication tokens or profile snapshots belong in search URLs. Saved searches contain validated definitions only.

## Lexical baseline: lexical-1.0

Query normalization applies Unicode NFKC, lowercase, whitespace collapse and punctuation separation, retaining word characters, `+`, `#` and `.`. Thus `Data—Analyst!` becomes `data analyst`; C++ and C# remain distinct strings. PostgreSQL normalizes searchable text with lowercase, punctuation separation and whitespace collapse. Full Unicode/locale equivalence is not guaranteed; this is not semantic search or a query language. Quotes are punctuation, not a phrase-only operator.

All distinct keyword terms must match somewhere across title, employer, required/preferred structured or current cached skills, description, responsibilities/qualifications, location, source name or source categories. Terms may occur in different fields; substring matching supports partial title/employer words. An empty/punctuation-only normalized query adds no keyword restriction. User `%` and `_` cannot become arbitrary SQL wildcards; ORM substring expressions escape them and use bound values. Skill extraction is reused from Phase 3 and must have an exact current public snapshot and extractor version. Incidental skills and arbitrary JSON metadata are not treated as required/preferred skill fields. New jobs without a cached analysis still search their original prose and structured skill rows; searching never calculates a candidate score.

Central lexical weights in `TEXT_WEIGHTS` are additive: exact normalized title +120, whole query substring in title +60, and per unique term title +20, employer +12, required/preferred skill +10, responsibilities/qualifications +5, description +2, location +2, source name/category +1. Repeated words do not repeatedly boost a term. These numbers describe query overlap only; they are not candidate suitability, eligibility, demand or hiring probability.

## Filter semantics and missing values

Different criteria combine with AND. Values in `employment_types`, `work_arrangements` or `skills` combine with OR within that list. A scalar and a plural variant, when both supplied, are separate AND constraints. The current UI exposes scalar employment/work mode and one skill field; the API and stored definitions can represent lists. Text title/employer/location use escaped case-insensitive substring matching. Country/source-region compares a complete source restriction label case-insensitively, or an explicitly empty restriction array meaning no country restriction. Null restrictions do not match; region membership and country-code equivalence are not invented. Location text and country restrictions are separate.

Known status, source, employment type/work mode and source-update/publication/verification timestamps are composable. Missing arrangements are not remote; missing status is not active. Date thresholds require timezone-aware ISO timestamps and exclude null dates. Experience filters compare overlapping disclosed min/max source ranges; they do not infer seniority from titles or candidate years. Only actual structured range fields satisfy those filters. Salary range overlap uses disclosed bounds, the exact selected currency and period. Missing bounds fail a range; no annualization or currency conversion occurs. Salary filtering/sorting needs both currency and period. Original publication is never replaced with first-seen/source-update time.

## Availability and sorting

The default preserves Phase 2: integrated records require active status, verification within 24 hours and no elapsed source deadline. Manual/legacy records retain their existing visibility, so their explicit closed/unknown statuses must still be read. `availability_scope=all` deliberately permits historical identity/status inspection. `requires_verification` finds nonclosed/nonexpired records with absent or old checks. Neither view mutates/deletes records or closes jobs because a source is down. Canonical presentation still suppresses unavailable integrated description, requirements, apply link and compensation; sensitive content/range filters do not positively match suppressed unavailable content. Saved jobs and application histories remain accessible by their original routes.

Sort options: `text_relevance`, `candidate_match`, `published_desc`, `verified_desc`, `title`, `employer`, `recent` (first collected) and `salary_desc` with units. Dates and salaries put nulls last. Title/employer use lowercase C-collation order. Every sort ends with canonical job UUID for deterministic ties. Candidate sorting uses only current nullable stored scores, descending/nulls last. Explicit eligibility mismatch remains a separately labeled property and can be filtered; a high relevance score never overrides eligibility. Search does not silently discard otherwise textually relevant jobs by candidate mismatch. Offset pagination is intentionally retained; concurrent source changes can move results between pages, so it is not snapshot pagination.

## Matching freshness without a second formula

Phase 3's ranking identity/formula is unchanged: `evidence-baseline-1.0.1+d5546bafea1c`. The search query computes the candidate snapshot fingerprint once, then selects that candidate's best current stored record per job, otherwise its latest stale record. A current record must match candidate/configuration/extractor identity, UTC assessment day, exact public job JSON (including child skills), status/source identity and verification/expiry context, plus present availability. Search shows current/null-insufficient, stale and not-calculated distinctly. Score, eligibility and required-coverage filters require current data. Stale/missing scores are null in the sidecar, never fabricated zeros; calculated zero is valid.

Migration `0004_search` adds nullable `job_context` and `assessment_day` to existing match rows so PostgreSQL can verify those inputs without loading every job into Python. Legacy rows remain intact and are conservatively stale for search until explicit refresh; an exact complete Phase 3 fingerprint match can safely populate their optional context on reuse. Reverted candidate data alone cannot refresh a changed job/date/config. New assessments persist context with the unchanged Phase 3 result. Detail/recommendation routes keep their original fingerprint checks.

## Frontend, privacy and performance

Search requests run on form submit; suggestions debounce 300 ms and use their own query keys. TanStack Query keys include all applied criteria, so an old response cannot overwrite a newer query. Controls reset page on submit/filter removal; URL changes/back navigation remount uncontrolled filters and synchronize keyword state. Invalid URLs show a correction/reset state without a job request. Successful writes invalidate relevant queries; failures stay visible. Login removes prior candidate query caches while preserving the authentication observer. Saved searches load through an owned POST that records last-use time. Comparison selection stores only public job IDs in memory across ordinary navigation and in the comparison URL, not permanent candidate data.

Migration adds saved-search ownership/uniqueness indexes and a job verification timestamp index. Existing status/source/publication/skill/match indexes are reused. No substring index or separate full-text service is introduced for 80 records. Query plans show database scans/joins with bounded page materialization; deep JSON validity checks and repeated lexical normalization remain costs to measure at larger scale. The genuine-record evaluation records local latency/EXPLAIN observations, not a capacity benchmark. No automated query-result cache can hide freshness changes.

Known limits include narrow lexical/skill vocabularies, incomplete source fields, structured-only experience filters, a single-provider evaluation snapshot, offset movement under concurrent ingestion, and private matching quality that remains independently unvalidated. Phase 5 and production hardening are separate future work.
