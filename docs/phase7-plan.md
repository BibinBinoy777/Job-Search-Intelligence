# Phase 7 audit and implementation plan

The existing React/FastAPI/PostgreSQL app has Alembic head 0005_resumes, 224 backend tests, 44 component tests and seven isolated browser workflows. Source manifest and database hashes are captured before modifications. Preserve the 80 genuine listings, original candidate/application/resume/matching records and prior archives; source verification may legitimately update/add genuine records through the existing pipeline, never synthetic development records.

Existing reusable automation: ingestion.cli.work_once, optional daily scheduler, source-level session advisory locks, partial active-run uniqueness, heartbeats/page checkpoints, transport retry budgets and source cooldowns. Existing source configuration already has schedule_hours/next_sync_at. Reuse these, the Himalayas adapter and current discovery/matching SQL; no second source client or scoring formula.

Extend that single worker with recovery/retry coordination, durable bounded downstream tasks, persisted canonical job-change events and a transactional delivery outbox. Add incremental migration 0006_automation for event sequence, retry lineage and notification/subscription/reminder/task records. Version events by actual meaningful content/availability transitions; exclude volatile observation timestamps. Persist event/task with the job update. No historical event backfill.

Subscriptions explicitly copy validated existing SearchCriteria (optionally from an owned saved search). Saving a search alone never subscribes. Future events only; immediate-on-next-worker-pass frequency, explicit pause, no promised digest or quiet hours. Strict active/recent verification is required for alerts, including legacy/manual records; score/coverage criteria use only exact current stored assessments. Never calculate a new score implicitly. Deduplicate overlapping subscriptions per candidate/job event.

Notifications have safe content and owned history/read state. In-app delivery is transactional and idempotent; optional server-side SMTP is opt-in and disabled without configuration. SMTP transport phases distinguish safe retries, permanent rejection and uncertain acceptance; sending left interrupted becomes uncertain, not blindly resent. Email contains only a generic workspace link and preference-management link, not job-feed/resume/profile data. No real email is sent during verification.

Reminders reuse owned application records and explicit candidate dates. Convert IANA-zone local times to UTC with DST-gap rejection and explicit ambiguous-time choice. Persist revisions, due tasks and one logical notification per revision; completion/cancellation/withdrawal prevents pending delivery. Show truthful queue/delivery states. No employer contact or application submission.

Add candidate notifications/alerts/reminders pages and operator-only schedule/task/outbox status on existing Sources. Keep existing routes/designs. Test source/event atomicity, scheduling/recovery, retry/idempotency, current-match thresholds, preferences, concurrent workers, uncertain SMTP, ownership, timezones and prior workflows in guarded _test/_browser databases. Run a bounded normal genuine-source synchronization after current provider documentation/terms verification, report actual outcomes and eligible count; do not create a live test candidate to pretend notification delivery. Complete docs, migration preservation, regression/build/security checks and local archive review; stop at Phase 7.
