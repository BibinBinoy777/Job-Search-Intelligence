# Local monitoring

Liveness and database/schema readiness remain separate. Expected revision is 0007_local_operations. API readiness does not establish worker supervision. The operator-only /api/v1/operations/health endpoint queries the DB, probes initialized private storage without exposing its path, combines persisted queue counts with actual worker/supervisor/backup records, and retains observation timestamps. Missing storage/records are not_initialized/not_recorded; email, scanning and production supervision remain not_configured/not_verified. Frontend availability is not inferred from an API request; startup separately probes HTTP.

Data sources extends the existing operations panel with the actual response, retaining source/run/task/delivery and uncertain-email controls. No uptime percentages or hard-coded healthy counters are added. A worker observation older than 45 seconds is a review signal, not proof that a long source request died. Disabled schedules are intentional. Exhausted tasks, interrupted runs, backlog and uncertain deliveries remain durable and visible. External monitoring delivery is optional/unconfigured.

Operational logs use JSON timestamp/severity/component, safe event identifiers and allowlisted correlation/task/run/resource/error-category fields. Arbitrary message interpolation, SQL parameters, exception text, request bodies, resume contents and credentials are not serialized. API correlation headers remain. The supervisor suppresses raw child stderr and persists safe exit/backoff metadata instead. IDs and metadata still require operator access protection.

Logs are ignored local runtime artifacts. No production shipper, automatic retention daemon, unattended boot service or external on-call channel is claimed. Configure rotation/archive policy for inactive logs and audit data; never delete active files or all runtime/storage data as cleanup. Inspect actual timestamps and DB work state together with process state.
