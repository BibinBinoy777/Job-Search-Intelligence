# Private storage, processing and deletion

The default root is `~/.job-search-intelligence/private-resumes`, configurable with `RESUME_STORAGE_ROOT`. This filesystem adapter never serves a public directory. Frontend trees and the project's public/dist roots are rejected. Objects use random profile/version UUID references and `.blob` suffixes, never user filenames. Paths are allowlisted, checked for containment and symlinks; files use exclusive creation, restrictive POSIX modes and fsync. No original is silently overwritten. A profile can hold 10 resumes, 20 versions per resume and 50 MiB total stored bytes by default. Uploads authenticate before parsing and use extension, MIME, magic signature and document-structure checks, plus both declared and actual streamed byte limits. Password-protected PDFs, macros, embedded active content and unsafe ZIP/XML structures fail safely.

**Malware scanning is not configured or performed.** A scanner protocol exists for a future real integration; default status is `not_configured`, never “clean.” Format validation and active-content rejection do not establish malware safety. The UI reports this limitation.

Parser inputs travel through stdin, not command-line arguments. Parser stderr is discarded, safe enumerated errors are returned, and document text is not logged. The Python child is bounded by a Windows Job Object or Unix address-space limit plus wall timeout, but it is not a complete filesystem/network security sandbox. Deploy untrusted parsing in an isolated service/container with denied network, least filesystem access and OS resource limits. Two-child capacity is per API process, not a cluster-wide quota.

Windows POSIX file modes do not establish production ACL isolation. Production requires a service-account-only storage ACL or private object bucket, encryption at rest and in transit, lifecycle/backup controls, least-privileged DB and storage identities, authenticated downloads, storage monitoring and a configured scanning policy. Do not map the private root into any static server, public bucket, source archive, frontend build or log system. Backups contain sensitive originals and extracted text and need equivalent access and retention controls.

Ownership derives from the authenticated session at every metadata, version, download, processing, evidence, review, preview, confirmation and deletion endpoint. Parent joins prevent ID substitution between versions/extractions and candidates. No arbitrary path or client-supplied user/profile identity is accepted. UI strings use React escaping. Existing origin checks and revocable cookie sessions remain enforced.

## Retention and recovery

Uploaded originals and extraction text persist until candidate deletion; no automatic expiry is implemented. Normal failed upload transactions unlink newly written files through rollback callbacks. Parser processes use in-memory input/output, so there are no parser temporary-document files. File-write failures remove partial objects. Processed failures retain the original version and a safe failure code for deliberate retry.

Deletion first commits `deletion_pending`, blocking further download/process/review/confirmation. It then unlinks every version idempotently and deletes the parent; foreign keys cascade versions, extraction runs, source text, proposals, evidence and document confirmation history. A filesystem failure returns 202 with deletion pending; retry DELETE to finish. If file deletion succeeds but the final database transaction fails, the committed tombstone remains with missing files and retry finishes database cleanup. The inverse order is deliberately avoided. The private directory itself may remain empty; no bytes remain for successfully deleted versions.

Previously confirmed profile facts remain independent candidate-owned profile fields and are retained after document deletion. Generic candidate audit events remain (action, resource UUID, user, timestamp), with no document contents, original filename or full source text. Document-specific provenance/confirmation rows are removed with the document; no dangling document FK is attached to retained profile facts. Backups and already downloaded local copies cannot be erased by this endpoint and follow the operator's retention policy.

A host/process hard crash between file creation and database commit can leave an unreferenced private object; a failed rollback unlink logs a generic cleanup-required event. Automatic orphan sweeping is not implemented. Operators must reconcile private objects against `resume_versions.storage_ref` during a maintenance window, retain referenced objects and pending deletions, and remove only verified unreferenced objects under the configured root. Never delete the whole storage root or reset candidate data as a cleanup shortcut. This is a documented operational limitation, not a claim of atomic distributed filesystem/database commits.
