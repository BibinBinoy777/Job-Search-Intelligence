# Search evaluation

Verification date: 2026-10-28, Asia/Calcutta. This evaluates software behavior and lexical specification rules, not real-world job suitability. Phase 3 matching quality remains independently unvalidated.

## Reproducible genuine-record check

From `apps/backend`, run `python -m app.modules.search.evaluation --output ../../docs/phase4-search-evaluation.json` against the existing development database. It is read-only: no jobs, users or matches are inserted. It intentionally uses a nonexistent candidate identity, so private candidate data is not read or disclosed. SQL queries still use the real search service/query builder. The evaluator alone loads the small genuine snapshot to independently construct expected filter sets; application search filtering and pagination remain in PostgreSQL.

The final observation contains **80 genuinely stored jobs**, **40 visible under the preserved default freshness rules**, and 40 outside default discovery. The explicit historical view returned all 80. Earlier checks saw 80 current listings; during the session gap the first 40 aged beyond the existing 24-hour verification window. No timestamp/status was rewritten to make them look fresh, and no source record was deleted. Counts naturally change with source verification and time.

Eight genuine-record rules agreed exactly with expected sets: partial title, employer, identified required/preferred skill, title+work mode+employment type, deliberately nonexistent keyword, missing candidate assessment not matching score >= 0, known original-publication threshold and USD annual salary threshold. The skill case returned 6 expected records; the USD/year case returned 13, while the original-publication threshold returned 0 because this snapshot has no usable original publication dates. Unknown dates did not become newest postings. Title pagination returned all 40 visible IDs exactly once in the same order as the corresponding full sorted result. A live browser additionally checked 24 unique IDs across two pages and exercised UI next/previous controls.

Exact-normalized-title specification precision/recall at cutoff 1 were both 1.0 in this tiny case. These metrics only confirm that an exact title ranks as the lexical rule specifies. They are not human relevance judgments, representative accuracy, unbiased model comparison or hiring probabilities. Queries/rules are agent-authored test expectations; no independent human labels or training are involved.

## Performance observation

The final seven local service calls for the selected exact-title query measured median **90.29 ms**, minimum **77.96 ms**, maximum **191.11 ms**. The bounded SQL page's `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` measured planning **2.193 ms**, execution **26.457 ms**, returning one row. Observed node types include index/index-only scans, sequential scans, nested loops, memoization, function scans, aggregates, sort and limit. These measurements reflect this machine, cache state, query and one-provider snapshot; they are not end-to-end browser latency or a load/capacity guarantee. Earlier overlapping checks produced slower timings, reinforcing that the environment matters.

Search counts/order/filters execute in PostgreSQL. Result materialization is capped at page size. Candidate context is loaded once; source/skill relationships and page saved flags are batched. The query-count integration test verifies that fetching four result rows does not introduce per-card query growth compared with one row. Deep public-snapshot comparison, normalized substring search and lateral current-match checks remain potential costs at larger scale. No unsupported large-scale speed claim or extra search infrastructure is introduced.

## Isolated coverage and final outcomes

The complete backend suite passed **143 tests**. New search tests cover normalization/punctuation, exact/weak lexical priority, mixed-field terms, combined AND/list-OR predicates, null location restrictions, unknown fields, salary units/currencies, real date fields/null ordering, all sort modes, ties across pages, invalid input, source freshness and historical redaction, current/stale/missing/insufficient matches, candidate skill/experience/education/preference/project changes, changed job inputs/verification/day/config, legacy-context refresh, grounded suggestions, comparison bounds/ownership, saved-search CRUD/ownership/constraints/quota and bounded query counts. Existing Phase 1–3 suites are retained.

The frontend suite passed **30 tests across 4 files**, including original assertions for a single main loading announcement. Saved-search loading now uses secondary plain text rather than duplicating the main live status. New tests cover invalid URL suppression, filters/sort/page reset, back navigation, delayed-response isolation, debounced suggestions, stale score display, comparison selection/unknowns, saved-definition operations and login cache isolation. The test-only unsupported `exact` options were removed because role queries already use exact string matching, and a mock's function argument was typed; assertions were not weakened.

All **4 isolated Chromium workflows** passed (Phase 1–4), and the final **genuine-job Chromium workflow passed**. The genuine flow covers real source attribution, combined search, pagination, comparison, save/track, saved-search load and cross-candidate rejection. Synthetic candidates are explicitly temporary QA data; no synthetic production job was inserted. Responsive screenshots were retaken after data settled, scrolling to top and waiting for the mobile navigation transition. This prevents loading/transition artifacts from being mistaken for a finished layout. Production TypeScript/Vite build, formatting/lint, migration/schema and dependency checks are recorded in [completion report](phase4-validation.md).

## Limits and future quality work

The genuine snapshot is small and drawn from one source; many fields are absent. Contradictory/closed/unknown conditions missing from the snapshot are covered with clearly synthetic isolated PostgreSQL fixtures. Substring terms can match broader text than a person expects; no semantic understanding, arbitrary Boolean syntax or complete Unicode equivalence is claimed. Cached skill extraction is conservative and incomplete. Offset pagination can shift when ingestion changes records. Legacy assessments require explicit refresh to populate SQL-checkable context. Search is not a source verifier and cannot make an aged record current.

Independent human relevance labeling, broader datasets, extraction error review, outcome evaluation, larger load tests and production security/operations remain future work. **No Phase 5 implementation or alerts/notification automation were added.**
