# Job alerts

Saved searches are reusable definitions. A candidate must separately create an alert subscription and enable job alerts in notification preferences. Global job alerts and email default off. Fifty subscriptions per candidate are supported. A saved-search copy is an owned, frozen criteria snapshot; editing/deleting the saved search does not silently edit the subscription. Subscription names are unique within the candidate.

Subscriptions support the existing validated search criteria, optional current score, current eligibility and required-skill coverage. They default to future events only, without historical backfill. Editing or resuming resets the future boundary. Paused/deleted subscriptions cannot authorize a pending delivery. Material updates require the subscription's separate include-updates option. Immediate means the next worker pass; no digest or quiet-hours feature is implemented.

Ingestion commits a source job update, durable job event and evaluation task together. New source identities create new_listing. A stable normalized snapshot detects material title, description, responsibilities, qualification/skill text, salary and employment/location changes. Required/preferred JobSkill records are included in that snapshot. Set-like source restriction/category order is normalized. Observation, cached verification and source-updated timestamps alone do not create material events. Source-supported status changes create availability_change audit events without active-job notifications. Content reverting later is a new version, not globally suppressed by an old fingerprint.

Per-job row locking and sequence uniqueness protect concurrent persistence; unchanged repeated pages create no event. Failed per-record savepoints roll back their event/task too. Partial runs retain only committed valid observations and never infer closure from absence. A newer content version supersedes older pending events.

An alert requires status active, a source verification within 24 hours, and an unexpired listing. This also applies to legacy/manual listings; legacy discovery visibility is not sufficient for an alert. Existing search SQL evaluates criteria and exact current candidate/job/day/config fingerprints. Score, coverage or eligibility conditions additionally require an assessed result and a real score. Missing/stale/insufficient results are skipped; they are not zero scores. No automatic match recalculation or later replay of skipped events occurs. Refresh matching before evaluating score-sensitive events. Matching relevance, eligibility and coverage remain separate; none is a hiring probability.

Overlapping subscriptions produce one logical candidate/job-event notification, with all matching subscription IDs recorded. Repeated workers cannot create another notification or another channel row. Delivery rechecks ownership, preferences, enabled subscriptions, future boundary, current criteria, content version and listing freshness. Historical notifications remain event records and do not promise the job is still open. Subscription activity lists owned notification outcomes, including suppressed channels.
